1. Концепция приложения
Polaris — система управления любительскими астрономическими наблюдениями, позволяющая пользователям:
- регистрироваться и управлять профилем;
- добавлять собственные телескопы и оборудование;
- просматривать каталог небесных объектов;
- получать информацию о погодных условиях для наблюдений;
- получать персональные астрономические квесты;
- регистрировать результаты наблюдений;
- автоматически проверять выполненные наблюдения.
Основной пользовательский сценарий:
1. Пользователь авторизуется в приложении.
2. Выбирает телескоп, с которым будет проводить наблюдения.
3. Просматривает каталог доступных небесных объектов.
4. Получает квест, например найти Марс или туманность Ориона.
5. Система проверяет погодные условия и видимость объекта.
6. Пользователь проводит наблюдение и отправляет результат.
7. Система проверяет координаты, время и условия наблюдения.
8. Пользователь получает подтверждение выполнения квеста.

3. Функциональная спецификация микросервисов
3.1 Auth Service — авторизация и безопасность
Назначение: управление учётными записями и проверка личности пользователя.

Функциональность:
- регистрация;
- авторизация;
- выдача JWT-токенов;
- обновление токенов;
- завершение сессии;
- проверка учётных данных.
Основные API:
Метод	Endpoint	Назначение
POST	/api/auth/register	Регистрация
POST	/api/auth/login	Вход
POST	/api/auth/refresh	Обновление токена
GET	/api/auth/me	Текущий пользователь

База данных: auth_db.

Основные сущности: Account, RefreshToken.
3.2 Catalog Service — каталог небесных объектов
Назначение: хранение и предоставление астрономической информации.

Функциональность:
- просмотр каталога;
- поиск небесных объектов;
- фильтрация по типу;
- получение характеристик объекта;
- добавление объектов в избранное.
Основные сущности:
- CelestialObject;
- ObjectCategory;
- Favorite.
Примеры типов объектов: планеты, звёзды, галактики, туманности, звёздные скопления.
Метод	Endpoint	Назначение
GET	/api/catalog/objects	Список объектов
GET	/api/catalog/objects/{id}	Информация об объекте
GET	/api/catalog/objects/search	Поиск
GET	/api/catalog/categories	Категории
POST	/api/catalog/favorites	Добавление в избранное
DELETE	/api/catalog/favorites/{id}	Удаление из избранного

База данных: catalog_db.
3.3 Equipment Service — управление оборудованием
Назначение: управление телескопами и оборудованием пользователей.

Функциональность:
- добавление телескопа;
- редактирование характеристик;
- удаление оборудования;
- получение списка телескопов пользователя;
- выбор активного телескопа.
Основные сущности:
- Telescope;
- EquipmentType;
- OpticalSpecification.
Метод	Endpoint	Назначение
GET	/api/equipment	Список оборудования
POST	/api/equipment	Добавление телескопа
GET	/api/equipment/{id}	Информация о телескопе
PUT	/api/equipment/{id}	Редактирование
DELETE	/api/equipment/{id}	Удаление

База данных: equipment_db.
3.4 Observation Service — управление наблюдениями
Назначение: регистрация и хранение истории астрономических наблюдений.

Функциональность:
- создание записи наблюдения;
- сохранение времени и координат;
- привязка к небесному объекту;
- привязка к телескопу;
- просмотр истории;
- получение статуса проверки.
Основные сущности:
- Observation;
- ObservationLocation;
- ObservationResult.
Метод	Endpoint	Назначение
POST	/api/observations	Создание наблюдения
GET	/api/observations	История наблюдений
GET	/api/observations/{id}	Информация о наблюдении
PUT	/api/observations/{id}	Редактирование
DELETE	/api/observations/{id}	Удаление

База данных: observation_db.
3.5 Quest Service — генерация и управление квестами
Назначение: создание астрономических заданий для пользователей.

Функциональность:
- получение списка доступных квестов;
- генерация заданий;
- подбор объектов для наблюдения;
- назначение сложности;
- отслеживание прогресса;
- завершение квестов.
Примеры заданий:
- Найти Марс.
- Наблюдать Луну.
- Найти туманность Ориона.
- Наблюдать три объекта из каталога Мессье.
Основные сущности:
- Quest;
- QuestTask;
- UserQuest;
- QuestProgress.
Метод	Endpoint	Назначение
GET	/api/quests	Список квестов
POST	/api/quests/generate	Генерация квеста
POST	/api/quests/{id}/start	Начало квеста
GET	/api/quests/{id}/progress	Прогресс
POST	/api/quests/{id}/complete	Завершение

База данных: quest_db.
3.6 Verification Service — автоматическая проверка наблюдений
Назначение: проверка достоверности пользовательских наблюдений.

Это один из наиболее интересных компонентов системы.

Функциональность:
- проверка координат пользователя;
- проверка времени наблюдения;
- проверка высоты объекта над горизонтом;
- проверка возможности наблюдения объекта в заданный момент;
- проверка условий видимости;
- формирование результата проверки.
Например, пользователь утверждает, что наблюдал Марс в 02:00. Сервис получает координаты наблюдателя, дату и время, определяет положение Марса и проверяет, находился ли он над горизонтом.

Основные сущности:
- VerificationRequest;
- VerificationResult;
- VerificationRule.
Метод	Endpoint	Назначение
POST	/api/verification/verify	Запуск проверки
GET	/api/verification/{id}	Результат проверки
GET	/api/verification/rules	Правила проверки

База данных: verification_db.
3.7 Weather Service — погодные условия
Назначение: получение и предоставление информации о погодных условиях для наблюдений.

Функциональность:
- получение прогноза погоды;
- получение облачности;
- получение температуры и влажности;
- оценка пригодности условий для наблюдений;
- получение прогноза на ближайшие часы.
Можно использовать внешний погодный API, например Open-Meteo.

Основные сущности:
- WeatherForecast;
- ObservationConditions.
Метод	Endpoint	Назначение
GET	/api/weather/current	Текущая погода
GET	/api/weather/forecast	Прогноз
GET	/api/weather/conditions	Оценка условий

База данных: weather_db (при необходимости можно кэшировать прогнозы).

4. Взаимодействие между микросервисами
Для лабораторной важно не просто создать семь отдельных приложений, а показать, что они действительно взаимодействуют.

Предлагаю использовать два способа взаимодействия.

Синхронное взаимодействие — REST API

Например:
- Flutter → API Gateway → Auth Service;
- Flutter → API Gateway → Catalog Service;
- Quest Service → Catalog Service;
- Verification Service → Catalog Service;
- Verification Service → Weather Service.
Асинхронное взаимодействие — RabbitMQ

Главный сценарий — автоматическая проверка наблюдения.
1. Observation Service

Пользователь отправляет результат наблюдения

Сохраняет наблюдение со статусом PENDING

2. RabbitMQ

Событие ObservationSubmitted


3. Verification Service

Получает событие и выполняет проверку

Проверяет координаты, время, высоту объекта и погодные условия

4. RabbitMQ

Событие ObservationVerified или ObservationRejected


5. Observation Service

Обновляет статус наблюдения


6. Quest Service

Обновляет прогресс связанного квеста


Таким образом, Observation Service не обязан ждать завершения проверки. Он принимает наблюдение и возвращает пользователю 202 Accepted, после чего проверка выполняется асинхронно.

Для надёжности стоит предусмотреть повторную обработку сообщений, защиту от дублирования событий и механизм Outbox. Последний можно добавить как дополнительное улучшение, а не как обязательную часть первой версии.

6. Организация баз данных
Каждый микросервис владеет своими данными. Другие сервисы не должны напрямую обращаться к его таблицам.
Микросервис	База данных	Основные данные
Auth	auth_db	Учётные записи, токены
Catalog	catalog_db	Небесные объекты, категории, избранное
Equipment	equipment_db	Телескопы, характеристики
Observation	observation_db	Наблюдения, результаты
Quest	quest_db	Квесты, задания, прогресс
Verification	verification_db	Запросы и результаты проверки
Weather	weather_db	Кэш прогнозов

Все базы могут физически находиться в одном экземпляре PostgreSQL, запущенном в Docker, но должны иметь отдельные базы данных и владельцев.

Например, Verification Service не получает доступ к catalog_db. Он запрашивает информацию через API Catalog Service.

Это позволит продемонстрировать принцип Database per Service.
7. Общие требования ко всем микросервисам
Каждый сервис должен самостоятельно запускаться и иметь:
- собственный main.py;
- собственный requirements.txt или pyproject.toml;
- собственный Dockerfile;
- собственный .env.example;
- собственную конфигурацию;
- REST API;
- обработку ошибок;
- структурированное логирование;
- подключение к собственной базе данных;
- эндпоинт /health;
- эндпоинт /ready;
- документацию Swagger.
Также необходимо предусмотреть:

Authentication: JWT с проверкой подписи токена на защищённых сервисах.

Authorization: разграничение доступа по ролям и владельцу ресурса.

Logging: JSON-логи с timestamp, service, level, request_id, message.

Error handling: единый формат ошибок, HTTP-статусы, обработка таймаутов и недоступности зависимостей.

Configuration management: настройки через переменные окружения, без секретов в Git.

10. Что должно работать в финальной версии
Я бы определил следующие критерии приёмки:
- [ ] Запускаются все 7 микросервисов через Docker Compose.
- [ ] Каждый сервис можно запустить независимо.
- [ ] У каждого сервиса собственная база данных.
- [ ] Пользователь может зарегистрироваться и авторизоваться.
- [ ] Защищённые API проверяют JWT.
- [ ] Можно просматривать каталог небесных объектов.
- [ ] Можно добавлять и редактировать телескопы.
- [ ] Можно создавать записи наблюдений.
- [ ] Можно получать и выполнять квесты.
- [ ] Weather Service получает реальные погодные данные.
- [ ] Verification Service проверяет наблюдения.
- [ ] RabbitMQ обеспечивает асинхронную передачу событий.
- [ ] Все сервисы имеют health checks и логирование.
- [ ] API документированы через Swagger.
- [ ] Есть интеграционные тесты межсервисного взаимодействия.
11. Что я советую не усложнять
Чтобы лабораторная не превратилась в разработку полноценного коммерческого продукта:
1. Не реализовывать реальную оплату.
2. Не добавлять машинное обучение для генерации квестов — достаточно алгоритма на основе правил.
3. Не делать сложную систему социальных функций.
4. Не использовать Kubernetes — Docker Compose достаточно.
5. Не делать отдельный frontend, если можно использовать существующий Flutter Polaris.
6. Не добавлять отдельный Notification Service: для данной предметной области он не обязателен.
12. Итоговая оценка концепции
Polaris Microservices
Соответствует основным требованиям задания
Тип: распределённая система управления астрономическими наблюдениями.

Архитектура: 7 бизнес-микросервисов + API Gateway.

Backend: Python + FastAPI.

Хранение: PostgreSQL, Database per Service.

Обмен сообщениями: RabbitMQ.

Контейнеризация: Docker Compose.

Клиент: Flutter.

Основная демонстрация: пользователь создаёт наблюдение, Verification Service проверяет его асинхронно, Quest Service обновляет прогресс.
